أمن واجهات برمجة التطبيقات (API)

ثلاث ثغرات شائعة تجعل الـ API هشّ، ومقابل كل واحدة الطريقة الآمنة الصحيحة. كود خاطئ وكود سليم جنبًا إلى جنب، عشان نفهم الفرق ونتعلّم نكتب كودًا آمنًا.

ابدأ المقارنة ↓ شغّل الكود محليًا
هشّ WHERE name = '' OR '1'='1'  →  يسرّب كل البيانات
آمن WHERE name = $name  →  مُعامَل، لا تسريب

لماذا هذا المشروع؟

واجهات الـ API هي العمود الفقري لأي تطبيق حديث (موبايل، ويب، خدمات). ولأنها تستقبل مدخلات من العالم الخارجي، فهي من أكثر النقاط التي يستهدفها المهاجمون. في هذا المشروع نأخذ ثلاثًا من أشهر الثغرات حسب تصنيف OWASP API Security Top 10، ونعرض لكل واحدة: الكود الخاطئ، كيف يُستغَل، ثم الإصلاح الصحيح — بأمثلة عملية بلغة C# على ASP.NET Core 8.

اضغط على التبويبات للتبديل بين الكود الهشّ والكود الآمن لكل ثغرة.

الخلاصة في جدول

الثغرة الخطر باختصار الإصلاح الجوهري
حقن SQL
SQL Injection		 تنفيذ أوامر على قاعدة البيانات وتسريب أو حذف بيانات. استعلامات مُعامَلة (Parameterized Queries) + التحقق من المدخلات.
مصادقة مكسورة
Broken Authentication		 كلمات مرور بنص صريح، توكن يُخمَّن، تخمين عنيف بلا حدود. تجزئة bcrypt/argon2 + توكن JWT موقّع + تحديد المعدل (Rate Limiting).
كسر التحكم بالوصول
IDOR / BOLA		 رؤية بيانات مستخدمين آخرين بتغيير رقم المعرّف في الطلب. التحقق من ملكية المورد على الخادم في كل طلب.

شغّل الكود على جهازك

مشروعان جاهزان بـ ASP.NET Core داخل مجلد api/ — واحد هشّ وواحد آمن — لتجرب الفرق بنفسك.

  1. ثبّت .NET SDK 8 أو أحدث.
  2. النسخة الهشّة (للتعلّم فقط): dotnet run --project api/Insecure ← المنفذ 5000
  3. في طرفية أخرى، النسخة الآمنة: dotnet run --project api/Secure ← المنفذ 5001
  4. جرّب الطلبات الموجودة في api/README.md وقارن النتائج.

صُمّم كمشروع تعليمي في الأمن السيبراني بواسطة نايف.
